# Interview notes

**What the application does.** Streamlit and `scripts.analyze` call the same Python pipeline. It reads `ticket_id,message` CSV, reports malformed or duplicate IDs by source row, and preserves the original text. Blank or exact greeting-only messages are ignored; a local classifier decides whether the other messages qualify. Qualifying tickets receive local sentiment and one structured OpenAI request for priority, a product/feature when supported by the message, and an unsent reply draft. Pydantic checks the output. SQLite stores processed, ignored and error outcomes separately; CSV/JSON exports keep the batch accounting. A failure stays an error with available partial results, and unchanged successful inputs can be reused without another paid call.

**What was fine-tuned.** I fine-tuned one pretrained `distilbert/distilbert-base-uncased` model for six categories: Bug Report, Feature Request, Billing Issue, General Inquiry, Customer Feedback and Non-Qualifying. Only message text enters its tokenizer; labels are targets, and IDs/provenance/split metadata do not become model features. The recorded run used a 128-token limit, dynamic padding, three epochs, learning rate `2e-5`, batch size 2 with four accumulation steps, and selected the epoch-3 checkpoint by validation macro-F1. Gradient accumulation combines gradients from four small batches before an optimizer step, making a larger effective batch feasible on a 4 GB GPU. The sentiment component reuses the existing classification weights of `cardiffnlp/twitter-roberta-base-sentiment-latest` locally; it was **not** trained. OpenAI generates the three remaining fields, with the local category and sentiment kept authoritative.

**Where the data came from.** The 600 English examples are synthetic. The assistant reviewed and corrected them under the user's explicit delegation; they have **not** been independently human-validated. Scenario groups and near duplicates were audited before freezing 420 training, 90 validation and 90 test rows with seed 42. Related messages stayed together, so class counts are not exactly balanced: Billing Issue has 50/11/15 and General Inquiry 90/19/15 across train/validation/test. The 90 test rows came from a separate test pool and were not used to select the checkpoint. Published assessment examples are visible acceptance fixtures, not unseen test examples. The test has now been consumed once for final reporting; future tuning requires a new independent test set.

**What was measured.** Validation accuracy was **0.9333** and macro-F1 **0.9305** on 90 rows. The fixed checkpoint got **89/90 correct** on the held-out category test: accuracy **0.9889**, macro-F1 **0.9889**, with **0/75 qualifying tickets incorrectly ignored**. The one category error was a Feature Request predicted as General Inquiry. These scores measure category classification on this small synthetic corpus, not real-customer or complete-pipeline accuracy. A separate real run of the three published assessment cases finished **2 processed, 1 ignored, 0 errors** after explicit retries. A 14-row mixed batch finished **7 processed, 2 ignored, 5 deliberate errors**. The final fresh 12-row sample run saved **5 processed, 3 ignored, 4 input errors**; its dark-mode ticket received **Low** priority despite the assessment expecting **Medium**. Automated tests use mocks for failure branches; these acceptance and final sample runs used the saved local models and the real configured OpenAI adapter. See [evaluation and acceptance evidence](evaluation.md) and [fresh sample record](../reports/submission/fresh_streamlit.json).

**Where it fell short.** Four mixed-case priority predictions disagreed with prewritten engineering references; the fresh sample's dark-mode priority also differed from the assessment despite a prior matching run. Initial live calls produced one schema failure and one timeout before explicit retries recovered both; the failures remain in the run history. Assistant review of the reply drafts found redundant questions, a request for partial payment details without an approved secure channel, and an unverified help/settings claim. Drafts need review before use. The separate sentiment evaluation file still has no independently written and labeled examples, so there is **no sentiment accuracy metric**. Physical browser upload/download verification remains pending; Streamlit AppTest does not establish that visual workflow.

**Why use this design instead of an LLM for every field?** Local models let the pipeline classify and filter before requesting generated details, and make category/sentiment behavior reproducible from saved weights. They also add model acquisition, memory and evaluation work, while the complete result still depends on an API for priority, feature and draft. We did **not** run an LLM-only comparison, so no relative cost, speed, privacy or accuracy benefit has been measured. The synthetic dataset and visible acceptance examples are the main limits on generalizing the measured category score.
